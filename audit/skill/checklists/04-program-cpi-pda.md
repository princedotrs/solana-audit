# 04 — CPI & PDA Safety Checklist

> Domain: On-chain Solana Program  
> Severity if missed: CRITICAL  
> References: Neodyme "Arbitrary Signed Program Invocation", Sealevel Attacks, QEDGen CPI properties

Every item below is a single verification step. Mark each `[PASS]`, `[FAIL-{severity}]`, `[PARTIAL]`, or `[N/A]`.

---

## 4.1 — CPI Target Validation

- [ ] **CPI-001**: Every `CpiContext::new()` first argument is a `Pubkey` (Anchor 1.0), NOT `.to_account_info()` (Anchor 0.x pattern) (1.x only; on 0.x the first argument is an AccountInfo, so check the field's type instead; see CPI-029). <!-- verified: anchor v1.0.0 lang/src/context.rs CpiContext::new(program_id: Pubkey, ..); v0.32.1 CpiContext::new(program: AccountInfo, ..) -->
- [ ] **CPI-002**: Every `CpiContext::new_with_signer()` first argument is a `Pubkey` (Anchor 1.0) (1.x only; on 0.x the first argument is an AccountInfo, so check the field's type instead; see CPI-029).
- [ ] **CPI-003**: Every CPI to SPL Token Program — the token_program account is validated as `spl_token::ID` or `Program<'info, Token>`
- [ ] **CPI-004**: Every CPI to System Program — the system_program account is validated as `system_program::ID` or `Program<'info, System>`
- [ ] **CPI-005**: Every CPI to Associated Token Program — validated as `associated_token::ID` or typed `Program<'info, AssociatedToken>`
- [ ] **CPI-006**: Every CPI to a DEX aggregator (Jupiter, etc.) — program ID is validated via `require_keys_eq!` against hardcoded known ID
- [ ] **CPI-007**: Every CPI to Metaplex — program ID validated against hardcoded `metaqbxxUerdq28cj1RbAWkYQm3ybzjb6a8bt518x1s`
- [ ] **CPI-008**: No CPI uses an `UncheckedAccount` as the program to invoke — the program account MUST be validated
- [ ] **CPI-009**: If remaining_accounts are passed through to a CPI, the target program ID is still validated
- [ ] **CPI-010**: For `invoke_signed` (raw Solana CPI), the program_id in the Instruction is validated before invocation
- [ ] **CPI-028**: For every `invoke`/`invoke_signed`, record where `Instruction.program_id` comes from: a constant, an SPL builder that validates it, or an alias that a dominating equality check pins to a constant on **every** control-flow path before the call. A check in one `match` arm, a check after the call, or a check on a different alias than the one put into the instruction does not count. Identify the callee from `program_id`, not from which account is missing in `account_infos` (FP-7).
- [ ] **CPI-029**: For every `CpiContext::new*` whose program is not a typed `Program<'info, T>`/`Interface`, open the wrapper's source for the pinned version. `anchor_spl::token::*` hardcodes `spl_token::ID` (not a finding). `anchor_spl::token_2022`/`token_interface` helpers pass the context's program (`ctx.program` on 0.x, `ctx.program_id` on 1.x) to the `spl_token_2022` builders, which reject any id other than SPL Token or Token-2022 (extension builders accept Token-2022 only). That is not an arbitrary-CPI finding, but check that the code does not assume one specific token program. The `token_2022_extensions` helpers take the program from an account field (`ctx.accounts.token_program_id` or `ctx.accounts.program_id`), not from the context's program. The extension-instruction helpers are safe because their builders accept Token-2022 only. **Exception:** the `token_metadata_*` and `token_group_*` helpers build through `spl_token_metadata_interface` / `spl_token_group_interface`, whose builders accept any program id (those interfaces are meant to be implemented by any program). - [ ] **CPI-030**: No untyped `Program<'info>` (it checks only `executable`) is an invoke target that receives PDA signer seeds or forwarded user signers. On Anchor 1.0.0–1.0.1 (and the 1.0.0 release candidates) the same applies to `Program<'info, System>`: the System program id equals `Pubkey::default()`, which those versions treat as "any program", so its key is unchecked. That matters when the code builds an `Instruction` from its key; the `anchor_lang::system_program::*` helpers hardcode the System id and are unaffected (KV-154). <!-- verified: anchor v1.0.0/v1.0.1 lang/src/accounts/program.rs is_unit_type = T::id() == Pubkey::default(); fixed in v1.0.2 (3eb1fb04) -->
- [ ] **CPI-041**: PDA signer privilege is never extended to a caller-chosen or untrusted upgradeable callee. The callee holds the PDA's signer privilege for the whole CPI and can pass it to nested CPIs, which makes it a confused deputy over every asset the PDA controls.

## 4.2 — CPI Parameter Validation

- [ ] **CPI-011**: `token::transfer` CPI — `from` account is the expected source (vault or user account)
- [ ] **CPI-012**: `token::transfer` CPI — `to` account is the expected destination (not attacker-controlled)
- [ ] **CPI-013**: `token::transfer` CPI — `authority` is the correct PDA or signer
- [ ] **CPI-014**: `token::transfer` CPI — `amount` is calculated correctly and matches expected value
- [ ] **CPI-015**: `token::mint_to` CPI — `mint` is the fund's shares mint (not an attacker-supplied mint)
- [ ] **CPI-016**: `token::mint_to` CPI — `to` is the investor's correct token account
- [ ] **CPI-017**: `token::mint_to` CPI — `authority` is the fund PDA (mint authority)
- [ ] **CPI-018**: `token::mint_to` CPI — `amount` matches calculated shares (not attacker-controlled)
- [ ] **CPI-019**: `token::burn` CPI — `from` is the investor's token account with their shares
- [ ] **CPI-020**: `token::burn` CPI — `authority` is the investor (they authorized the burn)
- [ ] **CPI-021**: `token::burn` CPI — `amount` matches the intended burn amount
- [ ] **CPI-022**: `token::close_account` CPI — `destination` is constrained to known recipients (fund PDA, investor, or treasury)
- [ ] **CPI-023**: `token::close_account` CPI — `authority` is the correct entity
- [ ] **CPI-024**: `token::close_account` CPI — the closed account is NOT the main vault (catastrophic if vault is closed)
- [ ] **CPI-025**: `system_program::transfer` CPI — source and destination are validated. The `from` of a System `Transfer` must be System-owned **and carry no data**; see CPI-031. <!-- verified: agave system program transfer_verified rejects `from` with data ("Transfer: `from` must not carry data") -->
- [ ] **CPI-026**: `token::approve` CPI — delegate and amount are validated, not granting unlimited approval
- [ ] **CPI-027**: `token::revoke` CPI — actually revokes the correct delegation
- [ ] **CPI-031**: SOL held by a program-owned account is paid out by a direct lamport debit by the owning program, preserving rent exemption. It is never paid by a `system_program::transfer` signed by the PDA, which always fails because `from` must be System-owned and carry no data. A withdrawal that depends on such a transfer is a locked-funds finding (High when it is the only exit).
- [ ] **CPI-032**: After direct lamport edits, the next CPI receives either all or none of the changed accounts (precisely: the changed accounts it receives must net to zero). Passing an unbalanced subset makes the runtime see a non-zero lamport delta when the CPI is pushed, and it fails with `UnbalancedInstruction` (runtime balance rule, FP-16). The failure is deterministic, so a value-moving path that always passes an unbalanced subset can never succeed: report it as locked funds or DoS when it is the only exit, not as a harmless revert. <!-- verified: agave v3.0.0 transaction-context/src/lib.rs push(): `!instruction_stack.is_empty() && accounts.get_lamports_delta() != 0` -> UnbalancedInstruction (only accounts synced into the CPI count); program-runtime/src/invoke_context.rs test case UnbalancedPush. In v2.1.0 the same rule is a caller-instruction lamport-sum comparison in sdk/src/transaction_context.rs TransactionContext::push -->
- [ ] **CPI-033**: Return data is consumed only after checking that the returned `program_id` equals the just-invoked, pinned callee. `None` is an error (not 0/default). Length and format are validated before decoding, values are bounded (0, `u64::MAX`), and the ordering/uniqueness of returned vectors is validated. Anchor's generated `cpi::Return<T>::get()` (and the `declare_program!` equivalent) verifies the program id only from 1.1.0 (#4411, #4624; on 1.2.x as well). That check compares against the id the CPI was sent to (`ctx.program_id`), so it pins nothing when that id is itself caller-chosen (CPI-029). It panics on mismatch or missing data rather than returning an error. On 1.1.0+ `get()` reads a snapshot taken right after the CPI. `get_unchecked()` skips the id check and reads the live return-data buffer. On ≤ 1.0.x, `get()` ignores the id and also reads the live buffer, so any CPI made between the call and `.get()` replaces the value (KV-152). <!-- verified: anchor v1.0.2 lang/syn/src/codegen/program/cpi.rs Return::get ignores key; v1.1.0 Return::get -> CpiReturnData::get(expected_program_id), snapshot taken via CpiReturnData::snapshot() right after invoke_signed, panic!() on mismatch, unwrap on None; get_unchecked calls live get_return_data(); same in lang/attribute/program/src/declare_program/mods/cpi.rs (commits 256da610 #4411 and 751d05c3 #4624 tagged v1.1.0+) -->
- [ ] **CPI-034**: Every `invoke_unchecked`/`invoke_signed_unchecked`, Pinocchio unchecked CPI or raw `sol_invoke_signed_*` call has a written justification. No data/lamports borrow of a passed account (including bytemuck/zero-copy views) is alive across it, and views are re-derived after it (KV-182).
- [ ] **CPI-035**: Hand-assembled CPI structures (`AccountMeta`/`AccountInfo` arrays, seed slices) are built only from validated accounts, their lengths match, and `is_signer`/`is_writable` are never more than intended.
- [ ] **CPI-036**: `get_processed_sibling_instruction` results are treated as hints. They are completed instructions at the same stack height under the same parent, newest first. They carry the program id, data and metas, but **not** their effects (balances actually moved, accounts created, fees withheld). Consumers decode the sibling fully (discriminator, mint, destination, authority, amount) and prefer a balance-delta check. For Token-2022 fee/hook mints, the requested amount differs from the received amount.
- [ ] **CPI-037**: After any `approve`/`approve_checked` of a delegate on a program-owned token account for an external pull, the handler approves the exact amount and revokes after the CPI. It then reloads and asserts `delegate.is_none() && delegated_amount == 0`, or it moves the exact amount into a per-operation account. PDA signer privilege is lent only to a pinned, trusted program (KV-165).
- [ ] **CPI-038**: SPL `approve` replaces the delegated amount; it does not add to it. Two approvals to the same delegate in one batch/CPI sequence leave only the second. Confirm whether additivity was intended. <!-- verified: solana-program/token program/src/processor.rs process_approve sets delegated_amount = amount -->
- [ ] **CPI-039**: No `Result` from `invoke`/`invoke_signed`, an SPL instruction builder, an Anchor CPI helper, a serializer write-back or a sysvar getter is discarded (`let _ =`, `.ok();`, `unwrap_or_default()`) on a value-moving or state-persisting path. Every built `Instruction` is actually invoked (KV-150).
- [ ] **CPI-040**: The boundary enumeration in §4.7 is complete for every CPI and account boundary.

## 4.3 — PDA Derivation Safety

- [ ] **PDA-001**: Every PDA is derived using all required seed components — no missing seeds that could cause collision
- [ ] **PDA-002**: Fund PDA seeds: `[b"fund", manager.key(), name.as_bytes()]` — verify all three present
- [ ] **PDA-003**: For each PDA in the program, list its seeds and verify all present in derivation
- [ ] **PDA-004**: Verify PDA seed order is consistent between `init` and all subsequent references
- [ ] **PDA-005**: Vault/treasury PDA seeds include parent account key — verify present
- [ ] **PDA-006**: Mint PDA seeds include parent account key — verify present
- [ ] **PDA-007**: Attestation/oracle PDA seeds include parent account key — verify present
- [ ] **PDA-008**: Access-control PDA seeds (whitelist, role, permission) include parent account key — verify present
- [ ] **PDA-009**: All custom PDAs above — verify seeds match in both derivation and usage (no mismatch between init and later references)
- [ ] **PDA-010**: Bump seeds are stored on first derivation and reused — not re-derived each time (saves compute + prevents bump mismatch)
- [ ] **PDA-011**: No PDA seed uses user-controlled variable-length data without length prefix (could cause seed collision). Apply the full seed-concatenation procedure in KV-026: a distinct literal first seed per account type, no literal that is a prefix of another, variable-length seeds last, and those seeds length-delimited or hashed.
- [ ] **PDA-012**: Fund name in PDA seeds — is there a max length? Can two funds have names that collide after truncation? A user string that one instruction stores and a later instruction uses as a seed (especially on an exit/withdraw path) is length-checked (≤ 32 bytes) **where it is first accepted**, or hashed to 32 bytes. A `require!(name.len() <= 32)` in the same handler as an `init` + `seeds` derivation runs too late, because the derivation fails first in `try_accounts`. An oversized seed in a single instruction only fails the caller's own transaction (Informational). `MAX_SEEDS = 16` includes the bump, so `find_program_address` takes at most 15 user seeds.
- [ ] **PDA-013**: PDA seeds do not include mutable state that could change (would orphan the PDA)
- [ ] **PDA-023**: Every PDA whose seeds reference the PDA's **own** stored fields (`seeds = [b"vault", vault.owner.as_ref()]`) binds the privileged actor to that field: `has_one = owner` with `owner: Signer`, or the seed derived from the `Signer`. For gating objects anyone can create (factions, pools, markets, guardian sets), the gate pins the intended instance through stored or global state. Checking only that the object "is genuine" is not enough (KV-144).
- [ ] **PDA-024**: A foreign-program PDA (`seeds::program = X`, native `find_program_address(seeds, X)`) takes `X` from a pinned program (`Program<'info, T>` or `address = X::ID`). Derivations never use an account's self-reported owner (`create_program_address(seeds, acct.owner)`) (KV-145).
- [ ] **PDA-025**: Bump provenance: classify the last seed passed to `create_program_address`. An instruction argument without a later `== find_program_address(..).1` comparison is High. A field of a Borsh-decoded instruction struct is High. A field of an account is safe only if it was written from `ctx.bumps`/`find_program_address` at an `init` that used `seeds` + bare `bump`. A stored canonical bump used with `create_program_address` is the recommended pattern, not a finding (KV-104).

## 4.4 — invoke_signed Safety

- [ ] **PDA-014**: Every `invoke_signed` call uses the correct signer seeds for the PDA authority
- [ ] **PDA-015**: Signer seeds array matches the PDA derivation exactly (same order, same components)
- [ ] **PDA-016**: Bump seed in `invoke_signed` matches the stored bump (not a different bump)
- [ ] **PDA-017**: `invoke_signed` is used (not bare `invoke`) when PDA is the authority — `invoke` with PDA authority will fail silently or be exploitable
- [ ] **PDA-018**: No instruction uses `invoke` where it should use `invoke_signed` (missing PDA signing)
- [ ] **PDA-019**: The instruction data passed to `invoke_signed` cannot be manipulated by the caller to change the operation
- [ ] **PDA-020**: For Jupiter CPI, the instruction data is either fully constructed by the program or validated
- [ ] **PDA-021**: `realloc` safety — grown bytes are zero-initialized AND the rent for the added space is not funded by the program/vault at an attacker-chosen size. Two sub-checks: **(a)** any `realloc(new_len, false)` (or `AccountInfo::realloc(_, false)`) that *grows* an account leaves the newly-added bytes NON-zeroed, so stale or attacker-influenced heap contents are later read as valid state — grows must zero-init the new region (`realloc(new_len, true)`, Anchor `realloc::zero = true` on a grow-after-shrink, or an explicit `data[old_len..new_len].fill(0)`); **(b)** the `realloc` target length is attacker-controlled AND the added rent is paid by the program or a program-owned vault (`realloc::payer = <program PDA / vault>`) rather than by the requester — an attacker repeatedly grows accounts to drain the vault's rent reserve. (PASS: every grow zero-inits the new bytes, and `realloc::payer`/the lamport top-up is the *requester*, with the size bounded by a `MAX_LEN` constant; FAIL: a `false`/non-zeroing grow whose new bytes are later deserialized, or a program/vault-funded realloc at a caller-chosen size — rent-exhaustion drain. Grep: `grep -rn --include="*.rs" -iE "realloc\(" programs/`) **(c)** Growth per account per instruction is at most `MAX_PERMITTED_DATA_INCREASE` = 10,240 bytes over its length at the start of the instruction (Anchor `realloc` returns `AccountReallocExceedsLimit` above it; AV-043). **(d)** On a shrink, Anchor's `realloc` credits all lamports above the new rent minimum to `realloc::payer`. Accounts that escrow SOL in their own lamports, or that receive donations, must not be shrinkable with an arbitrary payer. Refund only the released rent to the recorded original payer, or keep SOL value in a separate data-less PDA that is never resized (anchor.md §5, AN-022). <!-- verified: anchor v1.0.0 and v1.2.1 lang/syn/src/codegen/accounts/constraints.rs generate_constraint_realloc (shrink branch moves lamports() - minimum_balance(new_space) to payer) -->
- [ ] **PDA-022**: Every signing PDA is unique to the asset set it guards. Write down three things for each one: its authority domain (every token/lamport account it controls), its seed scope (global constant / mint / pool / user) and its binding path (the constraint that ties the state account supplying the seeds to this vault and destination). FAIL: the seeds are built only from shared values (a constant, a mint, a program-wide config) while an untrusted or permissionlessly creatable state account names the vault the PDA moves funds from. Test question: can an attacker create their own pool/position/escrow today whose seeds make the same PDA sign for someone else's vault? (KV-143)

## 4.6 — CPI Reentrancy & Composability

- [ ] **RE-001**: State mutations happen BEFORE external CPIs (checks-effects-interactions pattern)
- [ ] **RE-002**: If state is read after CPI, it's re-loaded (not using stale pre-CPI data)
- [ ] **RE-003**: Account reload after CPI uses `.reload()`. On Anchor ≥ 1.0.0, `reload()` re-checks the owner and the discriminator. Do the same for `LazyAccount::unload()` on < 1.2.0 (#4784). <!-- verified: anchor v0.29.0/v0.32.1 lang/src/accounts/account.rs reload() = try_deserialize only; v1.0.0 adds owner check; LazyAccount::unload re-runs try_from only from v1.2.0 (f170d119, #4784) -->
- [ ] **RE-004**: No CPI grants approval to an external program that could re-enter
- [ ] **RE-005**: Flash loan resistance: could an attacker borrow tokens, deposit, inflate NAV, and withdraw in one transaction?
- [ ] **RE-006**: CPI callee SOL-spend guard — Solana has no `msg.value`, so a callee can spend SOL from ANY signing account passed into a CPI (not just an explicit "amount" argument). Before an `invoke`/`invoke_signed` to a composed or user-supplied program, the caller records `signer.lamports()` and bounds the post-call drain. (PASS: pre-CPI lamports snapshot taken and a `checked_sub` post-CPI asserts the drain is within an expected bound; FAIL: a signing account is handed to an external CPI with no lamport accounting — the callee can siphon its full balance. - [ ] **RE-007**: Post-CPI ownership re-verification — an attacker-controlled callee can invoke System `assign` mid-CPI to steal an account's owner. - [ ] **RE-008**: No self-CPI through a caller-chosen program id. Executors of stored or caller-supplied instructions (multisig, DAO, routers, flash-loan receivers) reject `program_id == crate::ID` (or explicitly allow-list self calls), and write their effects (`executed = true`) before the CPI.
- [ ] **RE-009**: Before any CPI whose callee reads an Anchor `Account<T>` that was changed in memory (hooks, oracle adapters, sibling programs, self-CPI), the account is flushed with `exit(&crate::ID)?`. Otherwise the callee sees the last serialized state.
- [ ] **RE-010**: After a self-CPI (A→A) that writes an account the outer handler also holds, the outer handler reloads before writing. Otherwise the outer `exit()` overwrites the inner write (lost update / double spend).

## 4.7 — Boundary Enumeration (run until no boundary is left)

**Step 1 — list every boundary:** each `invoke`/`invoke_signed`/`CpiContext::new*`; each account whose owner or program comes from the caller (`UncheckedAccount`, `AccountInfo`, `Interface`, untyped `Program`); each `Option<Account<…>>`; each `remaining_accounts` iteration; each instruction-data / `try_from_slice` / zero-copy `load()`; each `get_return_data()`; each lamport move; each branch on a sentinel (`NATIVE_MINT`, `Pubkey::default()`, `u64::MAX`).

**Step 2 — ask the same questions at each:**
1. Unexpected account kind: uninitialized, owned by another program, executable, Token-2022 where SPL Token was assumed?
2. Non-standard token behaviour: TransferFee (received < sent; EXT-014), hook (extra CPI and accounts), confidential, NonTransferable, default-frozen, PermanentDelegate, MemoTransfer on the destination. Does the code use the requested amount or the measured delta?
3. Zero / max / empty: `amount == 0`, `u64::MAX`, empty `remaining_accounts`, empty `Vec`, zero-length seed string.
4. Return data: are the setter's program id and the length checked? The runtime resets return data to empty at the start of every invocation, including each CPI. So after A→B→C, if only C sets data, A reads it with C's program id.
5. Sentinel flowing into an SPL operation (`NATIVE_MINT` into `transfer_checked`, a lamport path receiving a real mint)?
6. Callee-controlled program or accounts: can the callee use the PDA signer privilege it receives (and pass it to nested CPIs) on other assets the PDA controls?
7. Unbounded caller-supplied fee, bonus or slippage parameter?

**Step 3 — native-SOL questions:** Are lamports measured (before/after) or assumed from `amount`? Is equality between an `amount` argument and the lamport transfer enforced? Is the fee taken on the native branch as on the SPL branch? Is excess SOL refunded, or stranded in a PDA with no sweep?

**Discipline:** each finding names the **boundary**, the **assumption** the code makes about it, and the **actual** behaviour under the corner case. Without all three it is a LEAD.
