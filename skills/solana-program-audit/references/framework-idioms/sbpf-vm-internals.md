# sBPF VM internals for unsafe review and PoC work

Use to judge whether an unsafe bug is exploitable and to explain it. **Check the deployed program's sBPF version and the cluster's feature gates first (runtime-context sheet).**

| Region | Virtual base | Notes |
|---|---|---|
| Program | `0x1_0000_0000` for text+rodata on sBPF v0–v2. On v3 (SIMD-0189) solana-sbpf 0.23 (the VM Agave 4.3 locks) moves read-only data to `0x0` and keeps bytecode at `0x1_0000_0000`; the earlier solana-sbpf 0.13 had the reverse (bytecode at `0x0`). Check the VM version of the target cluster | read-only; no ASLR — the same ELF gives the same addresses |
| Stack | `0x2_0000_0000` | sBPF v0: fixed 4 KiB frames separated by 4 KiB unmapped gaps (frame *d*: `r10 = 0x2_0000_0000 + 0x2000·d + 0x1000`); v1/v2 (SIMD-0166 dynamic stack frames): the program moves `r10` itself and `r10` starts at the top of the whole stack; v3 and later in solana-sbpf 0.23: fixed 4 KiB frames again, still without gaps. From v1 on there are no unmapped gaps (KV-181). Default VM `max_call_depth` 64 (a runtime config value); chains are also bounded by compute and CPI limits |
| Heap | `0x3_0000_0000` | 32 KiB default (more via `RequestHeapFrame`); bump allocator, dealloc is a no-op (no use-after-free reuse; exhaustion DoS applies) |
| Input | `0x4_0000_0000` | runtime-serialised: account count; per account a duplicate-marker byte (a duplicate is serialised as a 1-byte index + 7 bytes padding), `is_signer`/`is_writable`/`executable` flags + 4 bytes padding (original data length), key, owner, lamports, data length, data + 10 KiB realloc padding (aligned), `rent_epoch` u64; then the instruction-data length (u64) and data; then the program id. The layout is fixed but **the attacker chooses the contents** (accounts, order, duplicates, instruction bytes), so attacker bytes sit at predictable addresses |

- `call`/`exit` keep return addresses and saved registers in the VM's internal frame stack, not in addressable memory: a write primitive alone cannot redirect a return. Indirect calls (`callx`) could target any instruction in the text section in the versions the 2023 write-up targeted; newer versions tighten call semantics — check before downgrading.
- `sol_invoke_signed_rust(instruction, account_infos, n_infos, seeds, n_seeds)` takes raw pointers. The runtime validates privileges (signer/writable escalation, PDA derivation from the caller's id) but cannot tell whether the program meant to make the call.
- When a report claims "the OOB write only reaches padding", check the input layout: past one account's data and realloc padding lies the next account's serialised header or the instruction data; past a stack buffer lie adjacent frames (or the guard gap).
